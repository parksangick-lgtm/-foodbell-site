# 푸드벨 사이트 작업 흐름

브랜드 색·서체·문구 규칙은 `foodbell-brand` 스킬에, 프로젝트 전반 규칙은
`c:\galleypark\CLAUDE.md` 에 있다. **이 스킬은 "고친 것이 실제로 손님 화면에
가 닿았는가"** 만 다룬다 — 세 번 이상 반복해서 빠졌던 단계들이다.

---

## 1. css / js 를 고쳤으면 캐시 번호를 올린다

고쳐도 방문자 브라우저·서비스워커는 이미 받아 둔 옛 파일을 계속 보여준다.
`index.html` 의 `?v=` 숫자를 올려야 "다른 파일"로 보고 새로 받는다.

```bash
python 캐시버전올리기.py          # css/style.css, js/main.js, sw.js CACHE 를 함께 올림
python 캐시버전올리기.py --check  # 올리지 않고 확인만
```

- 크게 바뀌었으면 `sw.js` 의 `CACHE = 'foodbell-vN'` 도 올려야 풀린다.
  (`?v=` 만 올려서 안 풀린 적이 있다.)
- `저장.bat` 이 저장할 때마다 자동으로 점검한다 — 안 올렸으면 물어본다.
- 사진의 `?v=` 는 건드리지 않는다. 전부 올리면 손님이 사진을 다시 다 받는다.

**같은 교훈이 작업 노트에 세 번 적혔는데도 또 빠졌다.** 그래서 규칙을 더 크게
적는 대신 저장 단계에 자동 점검으로 붙였다. 반복해서 빠지는 수동 단계는
"더 잘 기억하기"로 고치지 않는다.

---

## 2. 휴대폰 화면 확인 — 도구가 그 폭을 정말 만들었는지 먼저 본다

헤드리스 크롬은 `--window-size=390` 을 줘도 뷰포트를 **약 485px** 로 잡는다.
그래서 390px 로 잘렸다고 본 화면이 실제로는 485px 이었고, **없는 버그를 세 번**
쫓았다(사라진 버튼 1회, 잘린 글자 2회). 매번 사이트는 멀쩡했고 측정이 틀렸다.

- 폭은 **390px `<iframe>`** 이나 CDP `Emulation.setDeviceMetricsOverride` 로 만든다.
- 캡처 전에 `document.documentElement.clientWidth` 를 **출력해서 390 인지 확인**한다.
- 외부로 나가는 폼 전송 시험은 **실제 크롬 창**에서 한다. 헤드리스(CORS 차단)와
  `curl`(403)은 막혀서 사이트가 고장난 것처럼 보인다 — 진짜 크롬에서는 200 OK 였다.
- 사용자가 쓰던 크롬 창을 죽이지 않는다(`taskkill chrome` 금지).
  `--user-data-dir` 을 따로 주고 새 인스턴스로 띄운다.

**"사이트가 깨졌다"고 말하기 전에, 확인 도구가 그 조건을 만들었는지 숫자로 먼저
확인한다.** 확인하지 않은 도구의 출력은 버그의 증거가 아니다.

### 규칙을 따른 도구도 다시 재야 한다

문서대로 390px `<iframe>` 을 만들어도 **스크롤바 폭만큼 좁게(375px)** 잰다.
그래서 "390 으로 확인했다"가 아니라 **되읽은 숫자를 그대로 보고한다.**
스크롤바를 없애거나(`html{scrollbar-width:none}`) 폭을 보정해 `clientWidth` 가
정확히 390 이 될 때까지 캡처하지 않는다.

### 측정용 사본을 만들었다면, 사본의 최신성부터 증명한다

원본을 베껴 만든 측정 페이지는 원본이 바뀔 때마다 **조용히 낡는다.** 낡은 사본은
오류를 내지 않고 **조금 틀린 숫자**를 내놓아 그 값으로 결정을 내리게 만든다.
사본으로 재야 한다면 원본에서 생성하고, 못 하면 재기 직전에 두 파일의 치수 값을
대조하는 단계를 절차에 넣는다.

### 상태를 남기는 화면을 시험하면 다음 관측이 오염된다

견적서·작업지시서는 입력을 자동저장한다. 동작 시험에 쓴 브라우저 프로필로 다시
캡처하면 **파일이 아니라 시험 결과가 찍힌다.** 동작 시험용과 화면 확인용
`--user-data-dir` 을 절대 섞지 않는다. 의심되면 프로필을 지우고 다시 찍어,
같은 화면이 두 번 같게 나오는지로 확인한다.

### 도구가 "무엇을 재는지" 코드로 확인한다

`캐시버전올리기.py --check` 는 설명문에 "올릴 필요가 있는지 알려준다"고 적혀
있지만, 실제로는 찾은 모든 `?v=` 에 대해 **무조건 다음 번호를 출력**한다. 즉
"필요한가?"가 아니라 "무엇으로 바뀌나?"에 답한다. **`--check` 출력만 보고 올리지
말고 `git diff --name-only` 에 `css/`·`js/` 가 있는지 먼저 본다.**

일반화: **언제나 같은 답을 내는 점검은 점검이 아니다.** 새 점검을 만들 때 첫
질문은 "무엇을 잡아내는가"가 아니라 **"이 도구가 '이상 없음'이라고 답하는 경우가
실제로 있는가"** 다.

### "없음"을 확인하는 점검에는 대조군을 같은 실행에 넣는다

노출·삭제처럼 **부재를 확인하는 점검**은 틀릴 때 "안전" 쪽으로 틀린다 — 원하던
답이라 아무도 다시 확인하지 않는다. 그래서 같은 실행 안에:

1. **양성 대조군** — 반드시 200 이어야 하는 경로(`index.html`)
2. **음성 대조군** — 반드시 404 여야 하는 무작위 이름

둘 다 기대대로 나올 때만 나머지를 믿는다. 추가로:

- **대조군은 대상과 "깨질 만한 성질"을 공유해야 한다.** 점(`.`)으로 시작하는
  파일을 검사하면서 평범한 이름으로 대조군을 두면, 통과가 **잘못된 안심**을 준다
  (실제로 `git cat-file -e <rev>:.vercelignore` 가 윈도우 깃배시에서 깨졌는데
  `index.html` 대조군이 통과해 "파일이 없다"로 오판했다). 한글 경로를 검사하면
  대조군도 한글 경로로 고른다.
- **차단을 확인하는 목록에는 실제로 존재하는 경로만 넣는다.** 없는 파일의 404 는
  차단의 증거가 아니다(`design/index.html` 은 애초에 없는 파일이었다).
  목록은 `git ls-files` 로 뽑는다.
- 비ASCII 경로는 **반드시 percent-encoding** 해서 요청한다(`urllib.parse.quote`).
  한글을 그대로 넣으면 요청이 깨지고, 그 404 는 "없음"과 구별되지 않는다.
- **"있는지 확인"은 결과물을 지우고 시작한다.** 이미 있는 것을 보고 통과로 읽으면
  고장 난 도구도 통과한다(바탕화면 아이콘 확인에서 실제로 두 번 그랬다).
- 숫자가 기대와 다르면 대상이 아니라 **세는 방법**부터 의심한다(`grep -c` 는
  "찾은 횟수"가 아니라 **"찾은 줄 수"** 다).
- 한글 값은 도구마다 다르게 읽힌다. 깃배시의 `hostname` 은 깨지고 PowerShell 의
  `$env:COMPUTERNAME` 은 제대로 읽는다. **문서에 적을 값은 제대로 읽히는 도구로
  다시 확인한다.**

## 3. 저장은 "올라갔는지"까지 확인해야 끝이다

`저장.bat` 창이 업로드 전에 닫히면 **커밋만 되고 안 올라간다.** 저장된 줄 알고
있다가 사이트가 안 바뀌어서야 알게 된다.

- 저장했다고 말하기 전에 `git status -sb` 가 `origin` 과 같은지 본다.
  `ahead` 가 있으면 아직 안 올라간 것이다.
- `시작.bat` 이 작업 시작 때 이것을 확인하고, 남아 있으면 올릴지 물어본다.
- `git add -A` 는 작업 폴더의 **새 파일을 전부** 올린다. 26MB 짜리 디자인 zip 이
  그렇게 올라간 적이 있고, 나중에 지워도 저장소 기록에는 남는다.
  `.gitignore` 에 `*.zip` `*.psd` `*.mp4` `__pycache__/` 가 들어 있고,
  `저장전점검.py --big` 이 5MB 넘는 새 파일을 잡아 물어본다.

## 4. 배포 상태는 기억하지 말고 한 줄로 확인한다

```bash
curl -s -o /dev/null -w "%{http_code}" https://foodbell.kr/
```

`200` 이면 정상. 도메인은 가비아, 호스팅은 **버셀(Vercel)** 이다(2026-09-18 전환).
`office` 브랜치에 push 하면 버셀이 자동 배포한다. 깃허브 페이지는 **되돌릴 곳으로
남겨 두었다.** 넷리파이는 **배포 중단** — 쓰지 않는다.

문서에 적힌 배포 상태는 낡는다. 실제로 `CLAUDE.md` 에 "404, 안 뜬다"고 적혀 있던
동안 사이트는 멀쩡히 떠 있었고, 그 낡은 기록 때문에 유료 호스팅으로 옮길 뻔했다.

### 주소는 한 곳에만 적히지 않는다 — 바꿀 때 같이 고칠 곳

같은 주소가 여러 파일에 복제돼 있어서, **한 곳만 고치면 나머지가 낡은 채 남는다.**
낡은 사본은 "없는 정보"가 아니라 **틀린 정보로 읽히는 정보**라 없는 것보다 비싸다.

| 고칠 곳 | 왜 |
|---|---|
| `바탕화면-바로가기.ps1` 의 `$site` | **동작 값** — 안 고치면 아이콘이 옛 주소를 연다 |
| `c:\galleypark\CLAUDE.md` 배포 절 | 작업 규칙의 기준 |
| `.github/workflows/deploy-pages.yml` 첫 주석 | 게시 주소 설명 |
| `.vercelignore` 첫 주석 | 제외 목록의 근거 |
| **`foodbell-brand` 스킬 4절·5절·6절** | 명함·현수막에 들어가는 주소 — **되돌릴 수 없는 결과물** |
| 이 스킬 4절 | 확인 명령 |

- **목록을 믿지 말고 `grep -rn "옛주소" .` 로 판정한다.** 목록 자체가 낡는 것이
  이 문제의 본질이다. grep 은 후보 제시자이고, 판정은 사람이 한다.
- **걸린 줄마다 "사이트 주소인가, 저장소 이름인가"를 갈라야 한다.**
  `작업방법.md` 의 `github.com/.../-foodbell-site` 는 **저장소 이름**이라 고치면
  안 된다. 실제로 걸린 10줄 중 바꿀 것은 5줄뿐이었다 — 목록만 믿고 전부 바꿨으면
  멀쩡한 것을 망가뜨렸다.
- **동작에 쓰이는 값이 하나라도 있으면 우선순위가 올라간다.** 낡은 문서는 오판을
  부르지만, 낡은 동작 값은 "고쳤는데 안 바뀐다"는 유령 버그를 부른다.

## 5. 파이썬 도구들

| 파일 | 하는 일 |
|---|---|
| `캐시버전올리기.py` | `?v=` 와 `sw.js` CACHE 번호 올리기 |
| `저장전점검.py --big` | 5MB 넘는 새 파일이 통째로 올라가려는지 |
| `저장전점검.py --cache` | css/js 를 고치고 캐시 번호(`?v=`)를 안 올렸는지 |
| `저장전점검.py --notpushed` | 지난번 저장이 GitHub 까지 갔는지 |
| `사진용량줄이기.py` | 사진 일괄 축소 (이 PC 에 ImageMagick 이 없다 — Pillow 를 쓴다) |

**`저장전점검.py` 의 옵션은 한 번에 하나만 먹는다.** `main()` 이 첫 옵션에서 곧바로
`return` 하므로, 세 개를 묶어 주면 **첫 것만 돌고 나머지는 조용히 건너뛴 채
종료코드 `0`("통과")으로 끝난다.** 실제로 안 올라간 커밋이 있는 상태에서
`--big --cache --notpushed` 가 "무거운 새 파일 없음 (통과)" 한 줄만 찍은 적이 있다.
셋 다 보려면 **세 번 부른다.** (`저장.bat`·`시작.bat` 은 이미 하나씩 부르고 있어
정상이다 — 틀리는 것은 이 표를 읽고 묶어 부르는 쪽이다.)

**도구 표에는 "무엇을 하는가"와 함께 "어떻게 불러야 하는가"의 제약을 적는다** —
한 번에 하나, 순서 의존, 인자 필수 같은 것. 제약이 빠진 표는 잘못된 호출을
유도하고, 하필 그 잘못된 호출이 "통과"로 끝난다. **코드도 배치 파일도 멀쩡한데
표 한 줄 때문에 점검이 무력화될 수 있다.**

**한글 묻기·긴 글은 배치 파일에 두지 않는다.** cmd 는 UTF-8 배치 파일에서
한글·괄호가 섞인 줄 뒤의 다음 줄을 갉아먹는 일이 있고(`echo` 가 `ho` 로 읽혔다),
git 은 한글 파일 이름을 `"\354\213\234..."` 로 바꿔 내보내 `if exist` 가 늘
실패한다. 둘 다 **조용히** 실패해서, 점검이 망가진 것과 걸릴 게 없는 것이
화면상 똑같아진다. 파일 이름·따옴표·인코딩이 얽히면 파이썬으로 옮긴다.

**경계를 이렇게 굳힌다: 배치 파일의 한글은 `echo` 안내문까지만, 입력을 받는 자리는
전부 파이썬.** `set /p "MSG=..."` 처럼 따옴표 안에 한글·괄호가 섞인 입력칸이
남아 있으면 옮긴다.

**그리고 이 경계는 배치 파일에만 걸리는 것이 아니다 — 셸이 해석하는 모든 자리에
걸린다.** heredoc(`cat > 파일 <<'EOF'`), 따옴표 안의 명령 인자, `-c "..."` 가 전부
같은 자리다. **셸에는 경로만 넘기고, 내용은 편집 도구로 파일에 직접 쓴다.**

- **판정 신호: 만들려는 내용에 역슬래시(`\`)가 하나라도 있으면 heredoc 을 쓰지
  않는다.** "얽히면"·"긴 글"처럼 판단이 필요한 기준은 부하가 걸리면 그냥 통과해
  버리지만, 역슬래시가 있는지는 보면 바로 안다. 정규식·JS·윈도우 경로가 대표적이다.
- 실제로 한 세션에서 두 번 연속 당했다. 따옴표 없는 `<<PY` 가 역슬래시를 먹어
  문자열 치환이 `target not found` 로 떨어졌고, JS 정규식 `/\n/g` 이 어긋나
  브라우저에서 `SyntaxError: Invalid regular expression` 이 났다. **두 번 다 편집
  도구로 파일을 직접 만들자 한 번에 통과했다.**
- **규칙의 범위를 그 규칙이 태어난 사례의 모양으로 적지 않는다.** 이 규칙이 오래
  "배치 파일" 한정으로 적혀 있어서, 같은 고장이 **도구 스크립트**라는 새 모양으로
  왔을 때 "내 얘기가 아니다"로 읽혔다. 범위는 사례가 아니라 **실패를 일으키는
  성질**(셸 인용을 지나가는 내용)로 적고, 사례는 예시 자리로 내린다.

**"지금까지 잘 돌았다"는 안전의 증거가 아니다.** 이 고장은 **바이트 위치**에 따라
불규칙하게 나타나므로, 그 파일 앞쪽에 몇 줄을 추가하는 것만으로 발현 조건이
바뀐다. 즉 **파일을 건드리는 변경이 곧 조건을 바꾸는 변경**이다. 취약한 구성을
새로 만들지 않는 것으로는 부족하고, **같은 구성이 이미 있는 자리를 함께 목록화**해
그 파일을 고칠 때마다 확인한다.

### 배치·스크립트 파일의 저장 형식 (한 번 틀리면 조용히 깨진다)

| 파일 | 줄바꿈 | BOM | 이유 |
|---|---|---|---|
| `*.bat` | **CRLF 필수** | 없음 | LF 로 저장하면 cmd 가 줄을 못 나눠 `'nul'`·`'NoProfile'` 을 각각 명령으로 실행한다 |
| `*.ps1` | 자유 | **UTF-8 BOM 필수** | 윈도우 PowerShell 5.1 은 BOM 없는 UTF-8 을 옛 인코딩으로 읽어 **파일 안의 한글 파일명이 깨진다**(`Test-Path` 실패) |

둘 다 겪었다. 원인을 짐작해서 고치기 전에 **바이트를 직접 본다** — `\n` 과 `\r\n`
은 화면에서 똑같이 생겼고, `grep` 으로 센 값도 틀렸다.

**단, 바이트를 볼 때 파이프를 끼우면 안 된다.** 깃배시의 `sed`·`grep`·`tr`·명령치환
(`$(...)`)은 `\r` 을 떼거나 줄 끝을 정규화한다. 그래서 보고 싶은 줄만 고르려고
`sed -n '3,7p' 파일 | od -c` 로 보면 **`\r` 이 사라진 화면**이 나온다. 그리고 그것은
오류가 아니라 **그럴듯한 정답의 모양**으로 온다 — `od -c` 는 정상 작동했고 화면에는
진짜 바이트처럼 보이는 것이 찍힌다. 실제로 이 출력을 보고 CRLF 파일을 LF 로 오판해
맞는 가설을 버린 적이 있다.

| 하고 싶은 것 | 이렇게 | 이렇게 하지 않는다 |
|---|---|---|
| 앞부분 바이트 보기 | `od -c 파일 \| head -20` — 자르는 것은 **뒤에서** | `sed -n '1,5p' 파일 \| od -c` |
| 줄바꿈 종류 세기 | 파이썬으로 `newline=""` 로 열어 `count(chr(13))`·`count(chr(10))` | `grep -c` 로 세기 |

**일반형: 판정하려는 성질을 그 자체로 건드리는 도구를 경로에 넣지 않는다.**
줄바꿈을 판정하는데 줄 단위 도구를, 인코딩을 판정하는데 인코딩을 바꾸는 콘솔을,
공백을 판정하는데 공백으로 쪼개는 셸을 끼우지 않는다. 이것은 2절 "확인 도구가
조건을 만들었는지 본다"의 **증거 파괴 판본**이다 — 2절은 도구가 조건을 *못 만든*
경우이고, 이쪽은 도구가 조건을 *만들어놓고 지운* 경우라 출력이 더 그럴듯해서 더
위험하다.

## 6. 되돌리기 어려운 작업 — 전제와 중단 기준

커밋·푸시·배포·DNS 전환처럼 **실제로 바깥에 나가는 작업**에 적용한다.

### 안전 전제는 "쓰이는 시점"에 다시 확인한다

시작할 때 `git status --porcelain` 이 비어 있는 것을 확인하고, 그다음 파일을
고친 뒤 시험을 돌려 **진짜 커밋·푸시가 나간 적이 있다.** 확인은 시퀀스의 시작에서
했고 위험한 행동은 끝에서 일어났으며, 그 사이에 상태를 바꾼 것은 **나 자신**이었다.

- 전제를 확인하는 코드는 **전제에 기대는 코드 바로 옆**에 둔다. 스크립트 첫 줄이
  아니라 마지막 줄 바로 위에서 다시 센다.
- 시험 전후로 `git status` 를 비교해 시험이 만든 파일이 섞이지 않았는지 본다.
- 부작용이 있는 것을 시험할 때는 **`--dry-run` 같은 안전 경로가 있는지 먼저**
  확인한다. 없으면 만들고 나서 시험한다.

### 중단 기준은 "절대 시각"으로 적고, 도구가 멈추게 한다

버셀 전환에서 DNS 는 40초에 퍼졌는데 **인증서가 15분 뒤에 나왔고 그동안 대표
주소가 죽어 있었다.** "10분 안에 안 되면 되돌린다"고 정해놓고 **10분이 지나도
되돌리지 않았다.** 결과가 좋아서 넘어갔지만 판단은 틀렸다 — 한 시간 뒤에 나왔다면
한 시간 내내 죽어 있었을 것이다.

- **"10분" 이 아니라 "02:25 까지" 로 적는다.** 상대 시간은 매번 다시 계산되고,
  계산하는 쪽은 늘 낙관한다.
- 감시 스크립트의 기본 동작은 **"계속 재기"가 아니라 "기준 시각에 멈추고 보고"** 다.
  판단이 아니라 도구가 멈추게 한다.
- **되돌릴 값을 먼저 화면에 적어두고 시작한다**(DNS 레코드 다섯 줄 등).
- 기준을 넘겨 기다린 판단이 **운 좋게 성공한 경우가 가장 위험하다.** 위반이
  보상받아 다음 위반의 근거가 되고, 그때는 결과가 같지 않을 수 있다.

## 7. 게시된 사진은 규칙이 바뀔 때 되짚는다

사진 개인정보 규칙(`foodbell-brand` 5절)은 **새로 만드는 결과물에만** 적용됐고,
규칙이 생기기 전에 이미 올라간 사진은 한 번도 그 기준으로 검사되지 않았다.
나중에 84장을 훑어 보니 **얼굴·번호판·비석 글씨가 실제로 게시돼 있었다.**

- **규칙을 새로 만들거나 강화하는 것 자체를 "기존 게시물 전체 재점검"의 방아쇠로
  삼는다.** 규칙만 적고 끝내면 이미 나가 있는 것은 영원히 검사되지 않는다.
- 점검은 **파일 이름·대체 텍스트로 하지 않는다.** Pillow 로 모아보기를 만들고,
  의심 가는 것은 **원본 해상도로 확대**해 눈으로 본다.
- **촬영정보(EXIF·GPS)도 본다.** 묘소 사진의 위치정보는 곧 묘소 위치 공개다.
  `사진용량줄이기.py` 를 거치면 빠지지만, 그 도구를 안 거치고 올린 한 장이면 샌다.
- **사진을 바꾸거나 가리면 주소 번호와 캐시 이름을 함께 올린다.** 파일만 덮어쓰면
  오프라인 캐시(`sw.js`)가 전에 방문한 손님 폰에 **가리기 전 사진**을 그대로
  보여준다. `?v=` 를 올리고 `sw.js` 의 `CACHE` 도 올리는 것까지가 한 동작이다.
- **공개 저장소에서 "지웠다"는 "안 보이게 했다"와 다르다.** 지운 사진도 git 기록에서
  그대로 꺼낼 수 있다. 완전 삭제가 필요하면 기록 재작성이라는 **되돌리기 어려운
  작업**이므로 6절의 기준을 적용하고, 사용자에게 먼저 묻는다.

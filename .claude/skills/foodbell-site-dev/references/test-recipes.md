## 규칙으로 못 만드는 읽기 실패 시험하기

(2026-11-18, 일정표 사장님 화면의 직원 확인 기록 — 시험은 `tools/sije_web/tests/test_doc_pages.py` 의 `test_daily_confirm_read_error_shows_line`)

시험 프로젝트에서는 사장님이 하는 읽기(config/share · share/{key} · marks)가 실패하지 않는다 — 규칙이 다 열어 준다.
옛 규칙을 시험 프로젝트에 올려 실패를 만드는 것은 일꾼에게 막혀 있다. 그래서 그 읽기 하나만 거절하는 가짜 `firebase-firestore.js` 를
끼우고, 그 위(store.js → doc-page.js → 화면)는 진짜로 돌린다. 화면 함수만 불러 보는 시험은 이어 주는 코드를 '읽어서 확인' 으로 남긴다.

1. `page.route` 로 `https://www.gstatic.com/firebasejs/<버전>/firebase-firestore.js` 를 작은 모듈로 바꿔 준다.

   ```js
   import * as real from '<같은 주소>?real';
   export * from '<같은 주소>?real';
   // 바꿀 함수만 이 파일에서 내보낸다 — 목표 하나면 거절, 아니면 real 로 넘긴다
   export function onSnapshot(ref, next, error) { /* 목표면 error({ code: 'permission-denied' }), 아니면 real.onSnapshot(ref, next, error) */ }
   ```

   이 파일에서 내보낸 이름이 `export *` 보다 이긴다. 그래서 화면의 `fs.onSnapshot` 은 가짜를, 나머지는 진짜 SDK 를 쓴다.
   진짜 모듈도 같은 `firebase-app.js` 주소를 불러서 앱 인스턴스는 하나다.
2. 바꿔 준 응답에 `Access-Control-Allow-Origin: *` 를 붙인다. 다른 출처의 모듈 스크립트라 없으면 안 불린다.
3. 가로채는 조건에서 `?real` 주소는 뺀다 — 글롭이 아니라 람다로 (`lambda url: url.endswith('/firebase-firestore.js')`).
4. 그 시험만 `browser.new_context(..., service_workers='block')` 로 연다. 사이트의 `sw.js` 가 gstatic firebasejs 를 캐시 먼저로 내주고,
   서비스워커가 답한 요청은 `page.route` 가 못 본다(서류 화면은 두 번째로 여는 쪽이라 이미 워커가 붙어 있다).
   여러 시험이 같이 쓰는 `new_ctx` 도우미는 바꾸지 않는다.
5. 가짜는 불릴 때 `window.__fsShim` 에 방식을 적는다. 시험은 그것부터 기다린 뒤 화면을 본다 — 가짜가 조용히 안 불린 채 나온
   통과 · 실패를 믿지 않으려고.
6. 같은 매개변수 묶음에 '오류 없음' 대조를 하나 둔다(그때는 `nokey`). 고치기 전에 돌려 오류 방식은 실패하고 대조는 통과하는지 본다.

## 로그인이 필요한 서버 기능을 PC 에서 실제로 불러 보기

(2026-11-10, 일정표 사진 채우기 `api/read-note.js` — 확인 기록은 `docs/superpowers/plans/2026-11-03-daily-schedule-photo-fill.md`)

`/api/read-note` 같은 서버 기능은 허락 목록에 있는 이메일의 파이어베이스 ID 토큰만 받는다. 사장님 휴대폰 없이도 PC 에서 부를 수 있다.

**먼저 사장님께 묻는다** — 사장님 계정으로 들어가는 일이다.

1. 실제 프로젝트 관리자 열쇠로 `firebase_admin.auth.create_custom_token(<사장님 uid>)` 를 만든다.
2. `https://identitytoolkit.googleapis.com/v1/accounts:signInWithCustomToken?key=<공개 웹 키>` 로 보내 ID 토큰으로 바꾼다.
   `Referer: https://foodbell.kr/` 를 붙인다.
3. ID 토큰은 메모리에만 둔다. 화면에 찍지도, 파일에 쓰지도 않는다.
4. 보낼 내용은 화면이 만드는 규칙 그대로 만든다(그때는 긴 변 2000 이하 JPEG q 0.85, 채우는 서류를 뺀 최근 서류의 이름 힌트, `day`).
5. 문서에는 아무것도 쓰지 않는다. 돌려받은 값만 본다.

채점:

- **보낸 사진의 픽셀 크기를 화면이 보낼 크기와 대 본다.** 대화에 붙인 사진은 캡처본이라(그때 720×961) 실제보다 작다 —
  그 사진으로 잰 정확도는 낮게 나오므로 '판정 못 함' 으로 적는다.
- **사장님이 친 기록은 메모의 받아쓰기가 아니다.** 다른 데서 온 칸(차량 · 출발 · 화장장 · 입금 메모), 사장님 오타, 메모에 없는 분류가 섞인다.
  다른 곳마다 원본 사진에 대 '잘못 읽음 · 원본에 없음 · 쓰는 방식' 으로 가른다(그때 자동 비교는 다름 19 · 기록에만 있음 12 였고, 진짜 고칠 곳은 채운 37칸 중 12칸).
- **기능이 표시 안 한 잘못 읽음은 따로 센다** — 그것이 위험한 쪽이다(그때 3개: 전화번호 두 자리, 금액 하나가 인원 × 단가로 나뉨).
- 비용(토큰 수)은 응답에 없다. 버셀 기록 줄(`{status, ms, in, out}`)이나 Anthropic 사용량 숫자는 사장님 로그인 뒤에 있으니, 부를 때 같이 부탁한다.

## 실제 저장소 문서 만들기 · 고치기

(2026-11-21, 빈 양식 '기본상' 더하기와 그 양식의 수량 11칸 고치기)

SKILL.md 6절대로 사장님께 먼저 묻고 실제 문서를 읽은 뒤에 한다.

### 새 문서

- `create()` 로 만든다 — 같은 이름이 있으면 실패하고 덮어쓰지 않는다.
- 만든 뒤 다시 읽어 넣은 값과 같은지 본다.

### 있는 문서 고치기 (`create()` 는 새 문서에만 맞는다)

1. 문서 전체를 파일로 떠 둔다 — 되돌릴 값이다. 파일은 작업 폴더가 아니라 `%TEMP%` 에 둔다.
2. 바꿀 칸마다 지금 값(이름 · 수량)이 '바뀌기 전' 으로 예상한 값과 같은지 본다. 하나라도 다르면 아무것도 쓰지 않는다.
3. `update()` 에 바꿀 칸의 경로만 준다(`items.L04.qty` 처럼). 문서를 통째로 다시 쓰지 않는다.
4. 다시 읽어 문서 전체를 '떠 둔 것 + 바꾼 칸' 과 비교한다(그때 11칸 바뀜, 나머지 19줄 · 다른 칸은 그대로).

- **사장님이 준 품목 이름은 실제 줄 순서와 대 본다.** '태추' 는 대추, '밥 1팩' 은 밤 1팩이었다 — 실제 순서(배 · 사과 · 감 · 밤 · 대추)가 증거였다.
  헷갈리면 바꾸기 전 → 후 표를 보여 주고 한 번에 묻는다. 그 표가 쓰기 허락도 된다.
- 낯선 값('없음' 등)은 고치기 전에 그 양식이 원래 쓰는 방식인지 본다 — 웃기의 '없음' 은 원래 그렇게 쓰고 있었다.

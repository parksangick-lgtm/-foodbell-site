# 직원용 링크 '푸드벨 일정' — 직원 '확인' 단추 (설계)

2026-11-04 ~ 11-05 사무실 PC.

사장님 결정:
- 화면은 직원용 링크 '푸드벨 일정'(`today.html`)이다. 알바비가 아니다.
- 직원별로 그 일정표를 봤는지 확인한다. 줄마다 확인하지 않는다.
- 직원은 그날 담당 이름을 단추로 고른다. 로그인은 없다.
  - 휴대폰이 이름을 기억한다.
  - 남의 이름도 누를 수 있다는 한계는 감수한다.
- 사장님은 일정표 화면과 밤 9시 텔레그램으로 본다.
- 확인한 뒤 사장님이 고치면 "고친 뒤 안 봄"으로 친다.
- 만드는 방식은 A다. 웹 저장소에 바로 적고 보안 규칙으로 좁힌다.
- 밤 9시 알림은 사무실 n8n 이 보낸다. 모두 봤으면 보내지 않는다.

## 1. 왜 · 지금은 어떻게 하나

**지금**
- 사장님이 저녁에 다음 날 일정표를 채우고 직원 단톡방에 사진을 보낸다.
- 일정표를 저장할 때마다 직원 게시판(`share/{암호}`)에도 올라간다. 직원은 단톡방 공지의 고정 링크 `today.html#암호` 로 본다.
- 누가 봤는지는 알 수 없다. 카톡 숫자는 몇 명이 읽었는지만 알려 준다.

**없애고 싶은 것**
- 직원에게 일일이 "봤어?"라고 묻는 일.
- 고친 뒤 옛 일정으로 나오는 직원이 생기는 일.

**성공 기준**
- 직원은 링크를 열고 자기 이름을 한 번 누르면 확인이 끝난다.
- 사장님 일정표 화면에 `직원 확인 2/4 · …` 가 바로 바뀌어 보인다.
- 밤 9시에 내일 일정표를 아직 안 본 사람과 고친 뒤 안 본 사람이 텔레그램으로 온다.

## 2. 실제 데이터 (2026-11-04, 읽기만 · 건수만 — 이름은 찍지 않음)

- 일일 일정표는 14장, 58줄이다. 58줄 모두 담당 칸이 채워져 있다. 한 장의 담당은 2~7명이다.
- 여러 명은 점(`.`) · 빗금(`/`) · 빈칸(`&nbsp;` 포함)으로 이어 적었다. "이름(메모)" 처럼 괄호가 붙은 줄이 1줄 있다.
- 이 글자들로 나누고 괄호 안을 빼면 모두 세 글자 이름이 된다.
  - 처음에는 길이만 보고 "이름이 아닌 글"이 있다고 추정했다. 모양으로 다시 세어 보니 틀린 추정이었다.
- 같은 날 일정표가 여러 장일 수 있다. 빈 것은 게시판에 안 올라간다. `share()` 가 일이 없으면 null 을 준다.

## 3. 구조

```
사장님 일정표 화면 ──저장── 직원 게시판 share/{암호}
  │                         entries.{일정표id} = { date, label, …, rows, names(새), at }
  │                         marks/{일정표id~이름} = { sid, name, at }   ← (새) 직원이 적음
  └─ 확인 줄(새) ◀── 바로 읽음 ──┤
직원 화면 today.html ── 이름 단추(새) ──┘
사무실 n8n 밤 9시(새) ── 읽기만 ── 텔레그램
```

### 3-1. 이름 나누기 · 확인 판단 — 작은 부품 하나 (새 파일, 시험 붙임)

이름 나누기 `staffNames(담당 칸 글)`
- 나누는 글자는 `.` `,` `·` `/` `、` `+` 와 빈칸(`&nbsp;` 포함)이다.
- 괄호 `( … )` 안의 글은 뺀다. 빈 조각은 버리고, 같은 이름은 처음 나온 하나만 남긴다.
- 이름이 아닌 글이 남으면 그 글이 그대로 단추가 된다. 지금 실제 기록에는 그런 글이 없다.

확인 판단 `confirmState(게시판 한 장, 확인 기록들)` → `{ done: [{name, at}], waiting: [name], stale: [name] }`
- 확인 기록의 시각이 그 일정표의 `at` 보다 앞이면 **고친 뒤 안 봄**이다.
- 지금 이름 목록에 없는 이름의 기록은 무시한다. 사장님이 담당을 바꾼 경우다.

이 부품은 사장님 화면 · 직원 화면 · 시험이 같이 쓴다. n8n 은 이 부품을 불러올 수 없어서, 같은 규칙을 n8n 코드 블록에 옮겨 적는다(3-5).

### 3-2. 게시판에 올리는 때 바꾸기 (`js/sije/store.js` `publishShare` · `daily-schedule.html` `share()`)

**`share()` 에 `names` 를 더한다.**
- 모든 줄의 담당 칸을 3-1 로 나눈 목록이다. 연기 · 취소한 줄의 담당도 넣는다(취소된 것도 알아야 한다).

**내용이 바뀐 때만 `at` 을 새로 찍는다.** 이번 설계에서 찾은 것이다.
- 지금은 사장님이 일정표를 **열기만 해도** 게시판에 다시 올라간다(`doc-page.js` 300번째 줄). 이때 `at` 도 새로 찍힌다.
- 그대로 두면 사장님이 열 때마다 모든 직원이 "고친 뒤 안 봄"이 된다.
- 그래서 `publishShare` 가 올리기 전에 이미 올라간 내용과 비교한다(`at` 은 빼고, 칸 순서와 상관없이).
  - 같고 지울 지난 날짜 칸도 없으면 쓰지 않는다.
  - 다르면 지금처럼 쓴다. 오타 하나라도 다르면 쓴다(사장님 결정).
- 덤으로 직원 화면의 "같은 날이면 가장 최근에 고친 것이 앞" 도 열기만 한 것에 흔들리지 않게 된다.
- 이미 올라간 옛 일정표에는 `names` 가 없다. 사장님이 한 번 **열기만 하면** 내용이 달라져(이름 목록이 생김) 다시 올라간다.

일정 카드 위(순번 · 메모 아래)에 확인 칸을 하나 둔다. 상태는 여섯 가지다.

### 3-6. 보안 규칙 (`firestore.rules`)

```
match /share/{key}/marks/{mark} {
  allow read: if true;                                   // 암호(경로)를 아는 사람만 닿는다 — 지금 게시판과 같음
  allow create, update: if exists(/databases/$(database)/documents/share/$(key))
    && request.resource.data.keys().hasOnly(['sid', 'name', 'at'])
    && request.resource.data.at == request.time          // 서버 시각만 — 휴대폰 시계로 못 꾸밈
    && mark == request.resource.data.sid + '~' + request.resource.data.name
    && request.resource.data.name in get(/databases/$(database)/documents/share/$(key)).data.entries[request.resource.data.sid].names;
  allow delete: if allowed();                             // 지우기는 사장님만
}
```

- 게시판 문서(`share/{key}`)의 규칙은 그대로 둔다. 직원은 계속 읽기만 한다.
- 일정표가 게시판에 없거나 `names` 가 없으면 규칙이 오류로 끝나 거부된다. 이것은 의도한 동작이다.
- 링크 암호를 바꾸면(`share_link new`) 옛 게시판이 지워진다. 그러면 옛 링크로는 확인을 적을 수 없다.
  - 다만 확인 기록 묶음은 저장소가 함께 지워 주지 않는다.
  - 그래서 `share_link.py` 의 `new` 가 확인 기록도 새 게시판으로 옮기고 옛 것을 지운다. 그래야 그만둔 직원이 옛 링크로 이름 · 시각을 못 본다.
- 남는 한계: 링크를 가진 사람은 남의 이름으로 확인을 누를 수 있다(사장님이 감수함).
- n8n 의 실행 기록(사무실 PC `database.sqlite`)에는 암호와 일정 내용이 남는다. 6시 알림이 이미 서류 전체를 읽는 것과 같은 정도다.

## 4. 가정 — 만들 때 먼저 확인할 것

1. **n8n 파이어스토어 블록이 `share/{암호}/marks` 를 읽는다.**
   - 지금 깔린 n8n 의 코드에서 칸 이름을 주소에 그대로 이어 붙이는 것을 확인했다(`…/documents/${collection}`).
   - 실제로 읽히는지는 첫 시험으로 본다. 안 되면 n8n 의 웹 요청 블록으로 같은 주소를 읽는다.
2. **카톡 안 브라우저도 기기 저장(`localStorage`)을 다음에 열 때까지 들고 있다.**
   - 못 들고 있으면 직원은 매번 이름을 누른다. 이름을 누르는 것이 곧 확인이라 손이 더 들지는 않는다.
   - 카톡 안 브라우저와 크롬(홈 화면 아이콘)은 저장소가 따로라서, 그 둘 사이에서는 이름을 한 번씩 고른다.
3. **직원 휴대폰의 카톡 안 브라우저에서 저장소 쓰기가 된다.**
   - 읽기는 지금 된다. 쓰기는 처음이다.
   - 사장님 기기가 아니라 **직원 휴대폰 한 대**에서 확인한다. 그 전에 휴대폰 폭 + 카톡 흉내로 한 번 돌린다.
4. **밤 9시에 사무실 PC 와 n8n 이 켜져 있다.**
   - 꺼져 있으면 알림이 안 오고, 그것은 "모두 봄"과 똑같아 보인다(사장님이 알고 조용을 고름).
   - n8n 이 살아 있는지는 월요일 9시 알림으로만 안다.
